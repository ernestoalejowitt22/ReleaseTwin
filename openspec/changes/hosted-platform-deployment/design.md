## Context

See `proposal.md` - Why. Everything today runs only via `dotnet run`/`next dev`/DynamoDB Local. Two AWS accounts are reachable from this machine: `quik.api.testing` (045807906966, shared with several unrelated projects' DynamoDB tables — explicitly not to be used) and `ealejo` (846136340491, the operator's own account, confirmed via `aws sts get-caller-identity`). `ealejo` has an admin-shaped IAM policy gated by an explicit MFA deny (`forcemfa-adminaccess`) — every AWS action beyond `sts:GetCallerIdentity` requires a short-lived session minted with an MFA code from the operator's own device, which only the operator can produce. This is a real, recurring step in any provisioning work against this account, not a one-time setup cost.

Verified during design (not assumed):
- **AWS Lambda supports .NET 10 as a managed runtime** (announced January 2026, supported for security/bug fixes until November 2028) — no container image is needed; a plain managed-runtime deploy works.
- **`Amazon.Lambda.AspNetCoreServer.Hosting`** adds Lambda support to an existing ASP.NET Core app additively: `builder.Services.AddAWSLambdaHosting(LambdaEventSource.HttpApi);` in `Program.cs` swaps Kestrel for the Lambda-aware server only when running under Lambda; running locally (`dotnet run`, and `web/`'s own e2e suite which boots the API via `dotnet run`) is unaffected.
- **Lambda Function URLs use the same payload format (2.0) as API Gateway HTTP APIs** — `LambdaEventSource.HttpApi` is the correct event source for a Function URL, not a separate enum value.
- **The GitHub OAuth flow is entirely API-side.** `web/`'s `startGitHubConnection` server action just calls the .NET API's `/api/connections/start`, which returns an authorize URL built by `GitHubConnectionFlowService` using `GitHubConnection:ClientId/ClientSecret/CallbackUrl` from the API's own configuration. `web/` (Vercel) never needs the GitHub client ID/secret — only the API does.

## Goals / Non-Goals

**Goals:**
- A real, reachable instance of the hosted platform: `web/` on Vercel, `ReleaseTwin.Hosted.Api` on Lambda, DynamoDB in `ealejo`.
- The operator can sign up for real (existing Clerk dev instance), create a project, connect a real GitHub account, issue a token, and run the CLI against the real deployed API from their own machine.
- Near-zero idle cost — nothing billed by the hour while unused.
- `dotnet run`/`next dev`/`npm run e2e` all keep working exactly as today; this change is additive to local dev, not a replacement for it.
- `terraform apply` for the actual infrastructure (DynamoDB + Lambda + IAM role + Function URL) can run from GitHub Actions via OIDC, not from a human's MFA'd session on every deploy — explicit user decision after weighing it against staying fully manual (see Decisions).

**Non-Goals:**
- A custom domain (explicit user decision — Function URL's and Vercel's default addresses are fine for now).
- Production Clerk instance (explicit user decision — stay on the existing dev instance/keys).
- Auto-deploy on push for `deploy-hosted.yml` (the actual DynamoDB/Lambda infra) — stays `workflow_dispatch`-only; that's a bigger call (it creates/updates real, billed resources) than the bootstrap layer. **Revised**: `bootstrap.yml` *is* now push-triggered (`main`, scoped to `hosted/terraform-bootstrap/**` and `hosted/terraform-state-backend/**`) per explicit user decision — safe to automate specifically because it's now idempotent (the OIDC-provider import fix) and low-stakes (an S3 bucket, a lock table, an IAM role — nothing that costs by usage or affects the running app).
- Secrets Manager / SSM Parameter Store — Lambda environment variables (encrypted at rest by AWS's own managed key by default) are enough for a single-operator pilot instance; revisit if this ever needs a second operator or real customer secrets.
- Billing/paid tiers — unchanged, Stage 1 free-only.
- Any change to `ReleaseTwin.Core`, adapter code, the CLI's behavior, or the hosted API's request/response contracts.

## Decisions

**AWS account: `ealejo` (846136340491), never `quik.api.testing`.** The latter is a shared account already holding tables from clearly unrelated projects (`ai-forms-*`, `quik-docs-*`, `lirj2dv.*`) — wrong blast radius and billing attribution for ReleaseTwin infrastructure, and its credentials here are permissions-scoped away from most infra actions anyway (confirmed: `apprunner:ListServices`/`ecs:ListClusters` both denied). `ealejo` is the operator's own dedicated account.

**Compute: AWS Lambda (managed .NET 10 runtime) + Function URL, over App Runner/ECS Fargate.** Chosen specifically for cost at near-zero traffic: Lambda's free tier (1M requests/month, forever, not a 12-month trial) makes this genuinely ~$0/month for solo pilot-testing use; App Runner/Fargate both carry a small but nonzero always-on baseline cost regardless of traffic. Explicit tradeoff accepted: cold starts after idle (order of 1-3s+, since AWS's SnapStart cold-start mitigation is Java-only, not available for .NET) — acceptable per explicit user decision, since this is pre-customer, low-frequency use.

**Function URL, not API Gateway.** A Function URL gives a public HTTPS endpoint directly from the Lambda resource itself — no domain, no ACM certificate, no API Gateway resource to configure — matching the explicit "no custom domain for now" decision. `AuthType: NONE` (Lambda-level/IAM auth off): the app already has its own two auth schemes (`ClerkJwt` for the dashboard, `ApiToken` for CLI ingest — see `hosted-react-frontend`/`cli-runner`), so a second, IAM-based auth layer in front would be redundant, not additive security.

**Lambda integration via `Amazon.Lambda.AspNetCoreServer.Hosting`'s `AddAWSLambdaHosting(LambdaEventSource.HttpApi)`, added to the existing `Program.cs`.** Not the older pattern of a separate `LambdaEntryPoint : APIGatewayProxyFunction` class — the `.Hosting` package's single-line addition keeps one `Program.cs` that works identically under `dotnet run` and under Lambda, which is what keeps local dev and `npm run e2e` unmodified (a hard requirement, not a nice-to-have — `web-cypress-e2e`/`registration-and-product-usage-e2e` both depend on `dotnet run --project ReleaseTwin.Hosted.Api` working exactly as it does today).

**All AWS infrastructure through the existing `hosted/terraform`, not a mix of terraform-for-DynamoDB and hand-run CLI commands for everything else.** The repo already has one `terraform` file and this AWS environment already leans on terraform broadly (confirmed: several `*-terraform-lock*` DynamoDB tables visible in the other, unrelated account) — a second, untracked deployment mechanism (`dotnet lambda deploy-function` run as a bare CLI command, no state, no plan/diff) for the Lambda function specifically would fragment the infra story for no real benefit. `hosted/terraform/main.tf` (or split into a few `.tf` files alongside it) grows to also own: the Lambda function resource (`aws_lambda_function`), its execution role (`aws_iam_role` + `aws_iam_role_policy`), and the Function URL (`aws_lambda_function_url`) — one `terraform apply` for the whole AWS footprint, matching how DynamoDB is already provisioned.

**Terraform doesn't compile .NET code, though** — `aws_lambda_function` needs a pre-built deployment artifact (a zip) to reference. That build step stays separate: `dotnet lambda package` (part of the same `Amazon.Lambda.Tools` package, its *build-only* subcommand — no AWS calls, no deploy, just produces the zip) runs before `terraform apply`, and terraform's `aws_lambda_function` resource points at that zip via `filename`/`source_code_hash`. This is the standard "build the artifact, let terraform own the infrastructure resource pointing at it" split, not a workaround.

**Two-pass apply, because of a real ordering dependency, not an accident.** The Lambda's environment variables include the GitHub OAuth Client ID/Secret/callback URL, but the GitHub OAuth App can't be registered until the Vercel URL exists, and Vercel can't be configured until the Function URL exists (terraform's own output). So: `terraform apply` #1 provisions DynamoDB + Lambda + Function URL with the GitHub-related variables defaulted to empty strings (the app already handles "GitHub connections are not configured yet" gracefully — see `ConnectionEndpoints.cs`); Vercel gets deployed using the Function URL output; the GitHub OAuth App gets registered using the Vercel URL; `terraform apply` #2 re-runs with the real GitHub values passed as `-var`, updating just the Lambda's environment variables in place (no resource recreation).

**DynamoDB: apply the existing `hosted/terraform/main.tf`'s table resource as-is**, with `table_prefix` set to something like `releasetwin-dev-` (mirroring the shared account's own `dev-`/`qa-`/`uat-` naming convention observed, even though this is a different, dedicated account — cheap insurance if `ealejo` ever hosts more than one thing later). No changes to the table resource itself; it was already written for exactly this.

**Lambda execution role: least-privilege, not admin.** Scoped to `dynamodb:GetItem/PutItem/UpdateItem/Query` (etc.) on the one table and its two GSIs specifically — not a broad DynamoDB policy, and nothing beyond DynamoDB. Standard Lambda basic-execution-role permissions (CloudWatch Logs) additionally required for the function to log at all.

**Vercel gets exactly the env vars `web/.env.local` already documents** (`NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY`, `RELEASETWIN_API_URL`) — `RELEASETWIN_API_URL` pointing at the deployed Function URL instead of `http://localhost:5199`. Nothing GitHub-related goes on Vercel (see Context — confirmed API-side only).

**A new, real GitHub OAuth App**, separate from Clerk, callback URL `<vercel-url>/connect/github/callback`, scope `read:user` only (matches the existing documented convention in README/`project-connections` — public info only, never `repo` scope). Its Client ID/Secret become Lambda environment variables (`GitHubConnection__ClientId`, `GitHubConnection__ClientSecret`, `GitHubConnection__CallbackUrl`), following the exact env-var-shape convention `Program.cs` already reads locally.

**GitHub Actions OIDC, not long-lived AWS secrets in the repo, and not reusing `ealejo`'s own IAM user.** Explicit user decision, made after weighing it against staying fully manual — a GitHub-hosted runner authenticates to AWS via a short-lived token exchanged through an OIDC trust (`token.actions.githubusercontent.com` → `sts:AssumeRoleWithWebIdentity`), never a stored access key. Critically, this does *not* mean handing CI the `ealejo` user's own credentials — those are permanently behind the `forcemfa-adminaccess` deny regardless of who presents them. It means a *new, separate* IAM role, trusted only for this one GitHub repo (`sub` condition scoped to `repo:ernestoalejowitt22/ReleaseTwin:*`), with its own least-privilege policy (exactly what `terraform apply` needs for this change's resources: `dynamodb:*Table`, `iam:*Role*`/`iam:PassRole` scoped to this role's own name, `lambda:*Function*`) — not admin, and not subject to the human-MFA requirement because it's a machine identity authenticated a different way.

**Remote state (S3 + a DynamoDB lock table), because GitHub Actions runners are ephemeral.** A local `terraform.tfstate` file only exists on whichever machine ran `apply` — a fresh GitHub Actions runner starts with no memory of it on every run, so without shared state, CI would either recreate every resource or fail on "already exists." This isn't optional once `apply` runs from CI; it's a hard requirement, not a nice-to-have. Bucket name includes the account ID (`releasetwin-terraform-state-846136340491`) since S3 bucket names are globally unique across all of AWS, not just this account.

**The bootstrap layer itself also runs from GitHub Actions, not from a human's local terraform — explicit user decision, made after weighing it against running it locally.** Nothing runs `terraform apply` from this machine, ever, matching the explicit ask.

**Bootstrap authenticates as a dedicated, narrowly-scoped IAM user (`releasetwin-bootstrap`) with a plain, standing access key/secret — not a short-lived MFA session pasted per run.** Explicit user decision after a second look: `forcemfa-adminaccess` is attached to the *`ealejo` user specifically*, not to "any credential in this account" — so a separate IAM user, deliberately never given that policy, sidesteps the MFA requirement for CI entirely rather than routing around it per run. This still needs exactly one MFA'd action, ever: creating that user, its narrow policy, and its access key — done once, directly in the AWS Console (MFA there is just the normal login, not CLI session-token juggling), not something repeated on every bootstrap run. The resulting key/secret lives as standing `AWS_BOOTSTRAP_ACCESS_KEY_ID`/`AWS_BOOTSTRAP_SECRET_ACCESS_KEY` repo secrets, kept permanently (not deleted after use) — GitHub Actions secrets are encrypted at rest and never re-displayed after creation, and the only realistic way to misuse them is already having write access to this repo, which is a solo-operator non-issue here. This is exactly the standing-service-account pattern already accepted as fine for `deploy-hosted.yml`'s own scope, just without OIDC — OIDC was preferred there specifically because that workflow runs routinely; `bootstrap.yml` runs rarely enough that the extra OIDC setup isn't worth it for this one narrowly-scoped identity.

**Bootstrap split into two terraform roots, not one, so only the truly static piece stays local-stated.** `hosted/terraform-state-backend` (the S3 bucket + DynamoDB lock table) is the one genuinely irreducible chicken-and-egg — nothing exists yet for its own state to live in, so it stays local, and since GitHub Actions runners are ephemeral, that state is lost the moment its job ends. Accepted specifically because a bucket and a lock table essentially never change once created (see Risks). `hosted/terraform-bootstrap` (the OIDC provider + CI role) is more likely to actually need a future update — new permissions, another repo, a rotated trust — so it uses the bucket/table `terraform-state-backend` just created as its *own* S3 backend, giving it durable, diffable state from its very first apply, unlike the bucket/table layer itself. Both jobs authenticate as the same `releasetwin-bootstrap` user (see above), since neither can use the OIDC role that `hosted/terraform-bootstrap` is itself in the middle of creating.

## Risks / Trade-offs

- [Cold starts after idle on every Lambda-hosted request — dashboard loads and CLI uploads alike] → Accepted per explicit user decision; revisit (App Runner, or Lambda provisioned concurrency) only once real usage frequency justifies the added cost.
- [No CI/CD means every redeploy is a manual `dotnet lambda package` + `terraform apply` / Vercel push — easy to forget a step, e.g. rebuilding the zip before applying, on a later change] → Accepted for now; the migration plan below documents the exact steps so they're repeatable by hand.
- [Two-pass `terraform apply` (empty GitHub vars, then real ones) is an easy step to forget on a future `terraform apply` if the `-var` values aren't persisted somewhere, silently reverting GitHub config back to empty] → Mitigated by writing the real values into a `terraform.tfvars` (gitignored, alongside the account's own secrets — never committed) once known, so a later plain `terraform apply` doesn't need them re-typed or accidentally omitted.
- [Function URL and Vercel's default domain are both effectively unstable identifiers — either could change if the underlying resource is ever deleted/recreated] → Acceptable at this stage (no domain, no customers depending on the URL yet); becomes a real reason to get a custom domain once this moves toward an actual pilot.
- [Reusing the single Clerk dev instance for both local dev and this deployed instance mixes their user/session data] → Accepted; low stakes for a single operator testing as their own customer, and matches the explicit "stay on dev instance" decision.
- [MFA-gated `ealejo` account means every provisioning/redeploy action needs the operator present to supply a code — cannot be scripted end-to-end by an agent] → Reduced to a single one-time action (creating the `releasetwin-bootstrap` IAM user, in the Console) by the dedicated-user decision above; every workflow run after that, including every future bootstrap re-run, needs no MFA and no operator presence.
- [If `ealejo` already has a GitHub Actions OIDC provider for `token.actions.githubusercontent.com` from another project (unverified — `iam:ListOpenIDConnectProviders` is itself behind the MFA deny, so this couldn't be checked without an MFA'd session), `aws_iam_openid_connect_provider` will fail to create with an "already exists" error] → Mitigation: if that happens, `terraform import` the existing provider's ARN into the bootstrap state instead of creating a new one; the provider itself is account-wide and safe to share across projects (the *role* trusting it is what's scoped to this repo).
- [`hosted/terraform-state-backend`'s own state is local and now guaranteed lost after its one CI run (not just "if the machine is lost," since it never runs locally at all) — a future re-apply would need `terraform import` for its 4 resources first] → Accepted; a bucket and a lock table are about as static as AWS resources get, and losing this layer's state doesn't affect anything already applied by the layers built on top of it.
- [`releasetwin-bootstrap`'s access key is a standing, non-expiring credential in GitHub secrets rather than a short-lived session] → Mitigated by scope (narrow policy, exactly what `bootstrap.yml` needs — S3/DynamoDB for the state backend, IAM/OIDC-provider actions for the trust and role, nothing else) and by GitHub's own secret handling (encrypted at rest, never re-displayed, masked in logs); the realistic misuse path is already having write access to this repo, which is a solo-operator non-issue.
- [A first real run confirmed a verb-enumerated bootstrap policy is fragile: the AWS provider makes read-back calls after creating a resource — `s3:GetBucketPolicy`, `dynamodb:DescribeContinuousBackups` — beyond the obvious create/read verbs, so the initial narrow action list failed partway through `terraform apply` on both `aws_s3_bucket` and `aws_dynamodb_table`] → Fixed by scoping the policy by *resource* (`s3:*`/`dynamodb:*` pinned to exactly the one bucket/table) rather than trying to enumerate every verb the provider might call — the resource pinning is what actually bounds blast radius here, not the verb list.

## Migration Plan

Order matters — later steps need URLs/values produced by earlier ones:

1. **Code**: add `AddAWSLambdaHosting(LambdaEventSource.HttpApi)` to `ReleaseTwin.Hosted.Api/Program.cs`; confirm `dotnet run` and `npm run e2e` still work.
2. **Terraform, main config**: extend `hosted/terraform` with the Lambda function, its least-privilege execution role, and the Function URL (`AuthType: NONE`), alongside the existing DynamoDB table resource; wire its backend to the not-yet-existing S3 state bucket/table (deterministic names, known in advance).
3. **Terraform, bootstrap configs**: `hosted/terraform-state-backend` (S3 bucket + DynamoDB lock table, local state) and `hosted/terraform-bootstrap` (OIDC provider + CI role, remote-stated in the bucket the first config creates).
4. **Create the `releasetwin-bootstrap` IAM user** (Console, the one MFA'd action in this whole plan — see Decisions), with a narrow policy covering exactly what `hosted/terraform-state-backend` and `hosted/terraform-bootstrap` need; generate its access key; store as standing `AWS_BOOTSTRAP_ACCESS_KEY_ID`/`AWS_BOOTSTRAP_SECRET_ACCESS_KEY` repo secrets. **`.github/workflows/bootstrap.yml`**: two sequential jobs (state-backend, then oidc-and-role), authenticated as that user. Run it once via `workflow_dispatch`; capture the CI role ARN from the run's summary.
5. **`.github/workflows/deploy-hosted.yml`**: `workflow_dispatch`-triggered, assumes the CI role from step 4 via OIDC (no stored AWS secret), builds the Lambda zip (`dotnet lambda package`), runs `terraform apply` for `hosted/terraform`. Set the CI role ARN from step 4 as the `AWS_DEPLOY_ROLE_ARN` repo variable first.
6. **Terraform, pass 1**: run `deploy-hosted.yml` with `table_prefix=releasetwin-dev-`, `region=us-east-1` (GitHub-related vars left at their empty defaults). Capture the Function URL from the run's summary.
7. **Vercel**: new project pointed at `web/`, environment variables set (see Decisions) with `RELEASETWIN_API_URL` = the Function URL from step 6, deployed on its default `*.vercel.app` domain.
8. **GitHub OAuth App**: register at github.com, callback URL using the Vercel domain from step 7.
9. **Terraform, pass 2**: store the real `GitHubConnection` values as repo secrets/variables; re-run `deploy-hosted.yml` — updates the Lambda's environment variables in place.
10. **Verify end to end**: sign up for real through the deployed Vercel URL, create a project, connect GitHub for real, issue a token, run the CLI from a local machine against the Function URL, confirm the dashboard reflects it.

No rollback beyond deleting/redeploying the individual resources — nothing here is stateful in a way that needs a migration-style rollback (DynamoDB data loss is acceptable pre-pilot; redeploying Lambda/Vercel is idempotent).
