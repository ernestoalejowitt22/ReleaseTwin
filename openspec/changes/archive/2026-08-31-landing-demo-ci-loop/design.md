  three-row fake table; the hero embeds `web/public/demo-flag-proof.svg` (an animated

- `integrations/github-action/` already runs the CLI with `--summary-json` and
  `render.mjs` posts a marker-keyed PR comment + a `ReleaseTwin` check run using only
  `GITHUB_TOKEN`.
- `docs/demo-videos.md` + `web/scripts/stitch-demo-video.mjs` already drive the real
  dashboard and the CLI's NAHA journey end to end, using LaunchDarkly + NAHA e2e
  credentials pulled from AWS Secrets Manager / `cypress.env.json`. That harness is the

- NAHA (`ernestoalejowitt22/NAHA`) is a private repo, same owner, with active CI. It has

## Goals / Non-Goals

**Goals:**
- The demo shows real Action output and real dashboard UI, regenerable by one script.
- The landing page communicates three claims visually: real merge gate, readable verdict,
  evidence-as-metadata-only.
- Dogfood the Action in a real repo (NAHA) as a side effect.

**Non-Goals:**
- A working Bitbucket Pipe or Bitbucket screenshots (static YAML snippet only).
- Making the stitched `.mp4` public.
- An interactive/click-through walkthrough.
- Live-rendering dashboard views from fake data on the marketing site.

## Decisions

### Committed screenshots regenerated by a script, not live-rendered React
The deep dashboard spans four views (run history, evidence viewer, trends, rollup).
Rebuilding those as marketing components with fabricated data multiplies maintenance and
drifts from the real theme/layout silently. Captured screenshots of the real dashboard,
plus a committed regen script, keep the assets honest and cheap to refresh.
*Alternative rejected:* extend the `DashboardPreview` pattern to all four views — too
much surface, and the spec's "only metadata leaves" claim is more credible shown in the
actual product than in a marketing mock.

### The PR comment panel is captured from a real run, not re-typed
The comment image comes from the actual GitHub PR (screenshot or the API-fetched comment
body rendered), so `render.mjs` is the single source of truth. A re-typed approximation
would be one refactor away from lying.

### NAHA is the demo repo
It is the app every RT demo already targets, so cases there are real integration checks,
not throwaway. Its private status is acceptable: the demo needs captured images, not a
public link. One PR is landed that fails the gate (a deliberately broken fixture or a
real caught regression), then a follow-up commit fixes it — giving both the ✗ and ✓
check states.
*Alternative rejected:* a fresh throwaway public repo — less credible ("they made a repo
just for the screenshot") and no ongoing value.

### Capture script lives in `web/scripts/`, reuses the video harness's credential path
No new secrets. It orchestrates: (1) fetch the target PR's check + comment via `gh` /
GitHub API, (2) run the existing Cypress dashboard walkthrough with `CYPRESS_VIDEO`/
screenshot capture against the seeded NAHA run, (3) write normalized images into
`web/public/`.

### Bitbucket: documentation only
Add a Pipelines YAML snippet to `web/src/app/(marketing)/docs/ci/` and a CI-agnostic note.
Deferred: a real `bitbucket-pipelines`-friendly render step (needs its own change — BB
has no check-runs API equivalent; it would post a PR comment via the BB API).

## Risks / Trade-offs

- **Screenshots go stale when the dashboard or `render.mjs` changes** → the regen script
  + a spec requirement that assets are script-produced; note it in the landing-demo spec
  and in `docs/`.
- **NAHA CI can't pull the RT CLI image** (GHCR visibility / token) → credential-preflight
  before wiring; the image is already `ghcr.io/ernestoalejowitt22/releasetwin/cli`.
- **A capture leaks non-test data** → spec requires review before commit; the adapter
  already redacts password fields, but raw screenshots are not redacted — reviewer's job.
- **Deliberately-broken NAHA fixture rots** → prefer capturing a real regression the gate
  caught; failing that, keep the broken case isolated and clearly named.
- **Landing page gets heavier** (4+ images) → use appropriately sized/compressed assets,
  lazy-load below the fold.

### Failing-gate panel: purpose-built broken case
The demo must show the check red (merge-blocked) and green. Add a clearly-named case
(`DEMO-GATE-1`) with a plausible assertion that a plausible one-line change flips —
capture red, commit the fix, capture green.
*Alternative rejected:* wait for a genuine caught regression — best story but
unschedulable, blocks the demo indefinitely.
