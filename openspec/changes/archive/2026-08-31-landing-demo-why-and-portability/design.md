## Context

See `proposal.md` — Why. The landing page (`web/src/app/(marketing)/page.tsx`) today
renders, in order: hero + animated terminal SVG → "One loop" (3 GitHub PR panels) →
"Dashboard" (2 screenshot panels) → trust → feature grid. Panels are static assets in
`web/public/demo/`:

- The 3 PR SVGs are generated by `web/scripts/capture-landing-demo.mjs` from
  `web/scripts/demo-summaries/{failed,passed}.json`, with wording mirroring
  `integrations/github-action/render.mjs` `renderBody()`.
- The 2 dashboard PNGs are captured by `web/cypress/e2e/capture-landing-demo.cy.ts` and
  copied by `web/scripts/capture-dashboard-demo.mjs`.
- Regeneration is documented in `docs/landing-demo.md`.

The Bitbucket Pipelines YAML snippet already exists on `/docs/ci`
(`web/src/app/(marketing)/docs/ci/page.tsx`, "Bitbucket, GitLab, and other CI" section),
rendered via the shared `CodeBlock` component. It is currently the only portability
surface and is not linked from or shown on the landing page.

Constraints from the specs: no Bitbucket PR screenshot, no copy implying a packaged
Bitbucket integration; the non-GitHub panel must derive from a real CLI run against the
same `--summary-json` contract; captured assets go through the test-data review.

## Goals / Non-Goals

**Goals:**
- A problem/value section on the landing page, above the demo, that the existing panel
  captions read as answers to.
- A non-GitHub CI panel in the demo that is concrete (not just prose) and provably
  portable, at low build/maintenance cost.
- Keep a single source of truth for the Bitbucket YAML — no second copy to drift.

**Non-Goals:**
- No change to the GitHub PR panels, the dashboard panels, or their capture pipeline.
- No new capture credentials or infra. The non-GitHub panel must be generatable from
  assets already in the repo.
- No component-level redesign of the page; this is one new section + one new panel entry.

## Decisions

### D1 — The non-GitHub panel is the YAML snippet **plus** a generated pipeline-log SVG

Resolves the proposal's open decision. The panel shows two things stacked:
1. the `bitbucket-pipelines.yml` snippet (the same string shown on `/docs/ci`), and
2. a generic terminal/pipeline-log SVG showing a real CLI gate run — the CLI's stdout
   and the non-zero exit that fails the step — styled as a CI log, **not** as any PR UI.

**Why both:** the snippet alone is honest but abstract (a visitor can't see that it
works); a log render alone loses the "one step, no wiring" point. Together they show
*config → result* the way the GitHub panels do.

**Why not build the Bitbucket pipe (proposal option C):** new integration repo, new
Bitbucket Reports/Comments API surface, ongoing maintenance, and a spec rewrite — all to
produce a second screenshot that says what the summary contract already says. Deferred in
the proposal.

**Why not snippet-only:** rejected as less concrete; the incremental cost of the log SVG
is low because the generator already exists (D2).

### D2 — The pipeline-log SVG is emitted by the existing `capture-landing-demo.mjs`

`capture-landing-demo.mjs` already reads `demo-summaries/failed.json` (the real
`--summary-json` output of the NAHA `DEMO-GATE-1` run) and renders SVG. Add one more
output — `pipeline-log.svg` — from the same `failed.json`: a monospace render of the
lines the CLI prints for that run plus a final `exit 1` / "step failed" line, in a
neutral CI-log visual style (no GitHub or Bitbucket chrome).

**Alternative considered — capture a real Bitbucket Pipelines run log.** Rejected:
requires a Bitbucket account, a mirror repo, and pipeline minutes; the output is the CLI's
own stdout, which we already have verbatim in the summary/run. A caption states the log
is the CLI running as a CI gate step.

**Alternative considered — reuse the hero asciinema recording.** Rejected: it records a
different (local, zero-cred) flow and is already the "under the hood" element; conflating
them muddies both.

### D3 — The Bitbucket YAML string becomes a shared constant

Extract the snippet currently inline in `docs/ci/page.tsx` into a shared module (e.g.
`web/src/lib/ci-snippets.ts`) imported by both the docs page and the new landing panel.
Satisfies the landing-demo spec's "sourced from the same snippet shown in `/docs/ci`
rather than duplicated" and its scenario that the two stay identical.

### D4 — Problem/value section is static JSX, sourced where possible from existing copy

The "what you gain" points map to claims already on the page (panel captions, the "Your
data stays put" trust section, the flag-proof hero copy). The new section is a short
lead-in + a compact two-column "without / with" list. The failure-mode line is new
marketing copy. No catalog/data-model involvement — it is not tier or entitlement content,
so it does not go through the plan catalog.

### D5 — Section order

`hero (title + CTAs)` → **problem/value** → `animated terminal SVG` → "One loop" (GitHub
panels) → **non-GitHub CI panel** (appended to the loop section) → "Dashboard" panels →
trust → features. This keeps the animated SVG as a supporting element below the
problem/value section, per the marketing-site spec MODIFIED scenario.

## Risks / Trade-offs

- **A hand-styled pipeline-log SVG could look "mocked".** → It is generated from the real
  `failed.json`, carries a caption naming it as the CLI's own CI-gate stdout, and uses a
  neutral log style with no vendor chrome so it is not mistaken for a product screenshot.
- **Two places render the Bitbucket YAML → drift.** → D3 makes it one shared constant; a
  spec scenario asserts identity.
- **The landing page grows longer; the demo could feel diluted.** → The non-GitHub panel
  is one entry appended to the existing loop section, not a new top-level section; the
  problem/value section is deliberately short (lead-in + one list).
- **Marketing claims in the "what you gain" table must stay true to the product.** →
  Every row restates a claim already made elsewhere on the site or in `/docs`; the one new
  sentence (the failure mode) is illustrative and hedged ("for example").

## Migration Plan

Pure marketing-site change. Ship in one PR: shared snippet constant, generator change +
regenerated `pipeline-log.svg`, new page section + panel, `docs/landing-demo.md` updated
with the new asset row. Verify with `npm run build` + `npx eslint` (per CLAUDE.md) and the
web vitest / capture-landing-demo specs. Rollback = revert the PR; no data or infra state.
