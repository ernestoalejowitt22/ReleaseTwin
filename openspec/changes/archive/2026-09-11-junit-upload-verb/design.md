## Context

See proposal.md — Why. This design covers how the verb attaches to the existing CLI, and the two
places where it deliberately does not reuse what is already there.

Verified against the code:

- `CliEntrypoint.ExecuteAsync` dispatches on `args[0]`: `init`, `new`, `view`, then `run`. Anything
  unrecognized falls through and is treated as **a directory of cases to run**. The `view` branch
  carries an explicit comment warning that a missing match there would make `view ./evidence`
  silently attempt a run instead.
- `IngestClient` already holds the base URL, the `Bearer` auth header, and an injectable
  `HttpMessageHandler` for tests. Its private `SendAsync` calls `EnsureSuccessStatusCode()`.
- `CliRunner` resolves `RELEASETWIN_API_TOKEN` and `RELEASETWIN_API_URL` from the environment
  dictionary, defaulting the URL to `https://api.releasetwin.example`.
- The hosted endpoint is `POST /api/ingest/junit`: raw XML body, optional `?release=`, returns
  `{"recorded": N, "runUrl": "..."}` on 201, and a plain-text explanation on rejection naming which
  cap or malformation was hit.

## Goals / Non-Goals

**Goals:**

- One verb, reusing the existing client's URL/auth/test seam.
- The platform's rejection text reaches the user unaltered.
- No core, adapter, or runner change.

**Non-Goals:**

- Parsing or validating the XML locally (proposal — the platform owns dialect handling).
- Any GitHub Action change (proposal — Explicitly not in this change).
- Evidence or screenshots; the endpoint accepts neither.

## Decisions

### D1 — A new client method, not a reuse of `SendAsync`

`IngestClient` gains `UploadJUnitReportAsync(byte[] xml, string? release, CancellationToken)` that
POSTs a raw `application/xml` body and returns a result carrying `Recorded`, `RunUrl`, and — on
failure — the platform's message.

It does not route through the private `SendAsync`, for two reasons. `SendAsync` builds a JSON or
multipart body from an object, which is the wrong shape entirely; and it calls
`EnsureSuccessStatusCode()`, which throws an exception whose message is the status line, **discarding
the response body**. The spec requires the platform's own explanation to reach the user, and that
explanation is the body. So the new method inspects the status itself and reads the body either way.

*Rejected: widening `SendAsync` with a raw-body mode.* It would add a branch to a method three
callers already depend on, to serve one caller that shares none of its evidence/multipart logic.

### D2 — Matched before the fallthrough, with a test that pins it

The verb is matched in `CliEntrypoint.ExecuteAsync` alongside `init`/`new`/`view`, above the line
that treats an unrecognized head as a cases directory. This is the same hazard the `view` branch
documents, so it gets the same treatment plus a test asserting that invoking the verb does not run
cases — the failure mode otherwise is silent and confusing (a "run" against a path that is a file).

### D3 — Read the file in the entrypoint, upload bytes

The entrypoint checks the file exists and reads it; the client takes bytes. This keeps the "file not
found" error local, off the network, and phrased in terms of the path the user typed — and keeps the
client free of file-system concerns, matching how it handles every other upload.

The bytes are sent verbatim. No `XDocument` round-trip, no encoding normalization: re-serializing
risks changing a document the platform would otherwise have accepted.

### D4 — A missing token is an error here, unlike during a run

`cli-runner` already specifies that a run with no token uploads nothing and treats the absence as
fine. That is right for a run, where uploading is a side effect. For this verb the upload is the
entire command, so a missing token exits non-zero with a message naming the variable. The spec calls
this asymmetry out so it reads as intentional rather than inconsistent.

## Risks / Trade-offs

- **The platform's rejection text is shown verbatim.** → It is generated by our own API and names
  limits, not user data. Worth re-checking if that endpoint ever starts echoing request content.
- **No local validation means a malformed file costs a round trip.** → Accepted deliberately: local
  validation is exactly the dialect-forking this change exists to avoid, and the round trip is one
  request that returns a precise message.
- **`--release` accepts any string.** → Same as the existing run-path release label, which the
  platform already treats as an opaque, length-capped grouping id.

## Migration Plan

None. A new verb; nothing existing changes behavior.
